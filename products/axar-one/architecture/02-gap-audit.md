## Findings

### Event flow and integration

| ID | Sev | Finding (evidence) | Fix (where) |
| --- | --- | --- | --- |
| G-EV-1 | **P1** | **Nothing reads the POS outbox.** `outbox_events` rows are written in the sale/refund transaction (`services.py:_sale_completed_event`), but there is no relay, no cursor and no consumer. CONNECT has its *own* SQLite outbox (`axar_connect/outbox.py`, "staging, no network dispatch"). Events can therefore never reach accounting. | One PostgreSQL outbox per producer + `event_consumers`/`inbox` tables + relay with cursor (ADR-0004, slice C1) |
| G-EV-2 | P1 | v1 envelope has no `aggregate_id/version`, `causation_id`, `actor`, sequence or currency. Consumers cannot order per aggregate, resume a stream or trace causality. `pos.sale.completed` lacks `simulated`, which the refund event has. | Envelope v2 (`contracts/events/envelope.v2.schema.json`); emit v1 and v2 in parallel until CONNECT migrates |
| G-EV-3 | P1 | Order, kitchen and drawer changes emit **no events**. The UI polls every 4 s (`app.mjs:POLL_MS`). Realtime (#18 guest status, KDS) has no source. | `order.*`, `kitchen.ticket.*`, `drawer.*` events + SSE fed from the outbox (slice C2) |
| G-EV-4 | P2 | Two independent "outbox" implementations: POS SQLAlchemy and CONNECT `sqlite3`. This is a competing source of truth that #15 forbids. | CONNECT consumes through the inbox; its staging table becomes an export queue owned by BOOKS |
| G-EV-5 | P3 | `register_id` is an integer in POS but a string in the CONNECT `CashSale` contract (converted in the adapter). This is harmless, but canonical ID types are not defined. | `03-data-ownership.md` canonical IDs |

### Domain model vs #14 / #16 / #18

| ID | Sev | Finding | Fix |
| --- | --- | --- | --- |
| G-DM-1 | **P1** | `Product` is at once inventory item, menu offer and price (`models.py:Product`). #14/#16 require item ≠ supplier SKU ≠ recipe ≠ menu offer/variant/modifier ≠ price/tax version. | Introduce `menu_offer` + `price_version`; keep `products` as the sellable snapshot source during migration (ADR-0003) |
| G-DM-2 | **P1** | **Payment = sale.** `Sale.payment_method='cash'` and one sale per order (`orders.pay_order_cash`). There is no tender table, so partial payment, split checks, mixed tenders and the `payment_intent` that #18 needs are impossible. | `payments` (tender) aggregate with its own lifecycle; the sale/receipt references tenders (ADR-0003) |
| G-DM-3 | **P1** | One overloaded order status `open|paid`; ticket `new|ready`. There is no separate fulfilment lifecycle, no cancel/void of sent items (`set_lines` forbids going below `sent_quantity`) and no waste disposition. | Separate order / payment / fulfilment state machines (`05-state-machines.md`) |
| G-DM-4 | P2 | No stock: no item master, movements, reservations or COGS. A sale can therefore not consume a recipe, and there is no risk yet of consuming twice. | #14 stock ledger (append-only movements, reservation ≠ physical) |
| G-DM-5 | P2 | No kitchen stations/routing; one global ticket list per location. | `station` on menu offer → ticket per station |
| G-DM-6 | P2 | Business timezone and day cutoff are **global settings** (`config.py`), not per location/legal entity. Multi-site in other zones would be wrong. | `location.timezone`, `location.day_cutoff` with effective dates |
| G-DM-7 | P2 | No legal entity. Tenant = company; VAT registration, receipts and GL per legal entity are impossible for multi-entity groups (#15). | `legal_entities` under tenant; location → legal entity |
| G-DM-8 | P3 | Product price is not versioned. Historic sales are safe (line snapshot), but quotes/menus have no effective dating. | `price_version(valid_from)` |

## What is already solid (keep)

- Money in integer cents and server-side pricing, with versioned VAT, half-up per-line VAT and cumulative cash rounding, all tested.
- Idempotency keys bound to request hashes; crash-safe client journal; definitive vs uncertain error rules.
- Conditional-UPDATE / compare-and-swap guards, verified on PostgreSQL with real lock interleavings.
- Append-only sales/refunds/outbox/audit enforced by the ORM **and** by database grants.
- RLS tenant isolation with a non-owner app role; server-side sessions, device binding, step-up approvals.

## Priority order (proposed DAG, see `01-system-context.md`)

1. **C1:** outbox v2 + relay + inbox + observability. Fixes G-EV-1/2, G-OPS-1, and is the foundation for everything after.
2. **C2:** order/fulfilment events + SSE with cursor and resume + KDS stations. Fixes G-EV-3, G-DM-3, G-DM-5 and covers the remaining part of the owner's realtime requirement.
3. **C3:** payments aggregate (tenders, payment intent, sandbox provider, webhook inbox). Fixes G-DM-2 and is a prerequisite for #18.
4. **C4:** menu offer / price version / item master + stock ledger (#14). Fixes G-DM-1, G-DM-4.
5. **C5:** guest ordering vertical slice (#18) on C1–C4.
6. Then legal entity / per-location time (G-DM-6/7), reconciliation, the operating profiles of #16.
